**Definições operacionais e variantes.** Todas as métricas são calculadas numa janela de observação de 12 meses (1º de outubro de 2025 a 1º de outubro de 2026), considerando apenas o *default branch* de cada repositório. Como o GitHub não registra deploys nem falhas em produção, cada métrica DORA é estimada por um *proxy*, descrito a seguir.

*Deploy.* Na definição principal, um deploy é uma *release* publicada no GitHub, com `draft = false` e `prerelease = false`. Pré-releases e tags sem release entram apenas nas variantes da análise de sensibilidade (RQ 07).

*Deployment frequency (RQ 01).* Número de releases publicadas na janela dividido pelo número de semanas da janela (≈ 52,1), em releases por semana.

*Lead time for changes (RQ 02).* Para cada release R da janela, os commits entregues são obtidos comparando R com a release publicada imediatamente antes dela (`compare/{anterior}...{R}`), seguindo a paginação da API até o fim. A data de um commit é a data de autoria (`commit.author.date`). Usamos duas variantes: (a) **por release**, a diferença entre a publicação de R e o commit mais antigo entregue por ela, resumida no repositório pela mediana entre as releases; e (b) **por commit**, a diferença entre a publicação de R e cada commit entregue, resumida pela mediana de todos os commits de todas as releases. A primeira release da história do repositório não tem anterior e é ignorada; releases cujo `compare` retornou HTTP 404 (tag apagada ou reescrita) também são ignoradas e contadas [N = 2 na amostra da Sprint 1]. A variante (a) é sensível a um único commit antigo "esquecido", enquanto a mediana da variante (b) praticamente não se altera com ele.

*Change failure rate (RQ 03).* Usamos duas variantes. (a) **Proxy de CI:** número de execuções de workflow com falha dividido pela soma de falhas e sucessos, considerando apenas execuções disparadas por `push` no *default branch*; `conclusion` igual a `success` é sucesso, `failure`, `timed_out` e `startup_failure` são falha, e os demais valores (`cancelled`, `skipped`, `neutral`, `action_required`, `stale` e execuções em andamento) são ignorados. Essa variante mede falha de *pipeline*, não falha em produção. (b) **Proxy de entrega:** uma release R é considerada falha se uma *release corretiva* que corrige R for publicada em até 7 dias depois dela; o CFR (b) é o número de releases que falharam dividido pelo número de releases avaliadas. Releases publicadas nos últimos 7 dias da janela não podem ser avaliadas e ficam fora do denominador (censura) [N censuradas].

*Release corretiva.* Uma release é corretiva quando seu objetivo principal é corrigir um defeito recente. A heurística automática compara cada release com sua **predecessora**. Como [32] dos 100 repositórios iniciais mantêm linhas de versão paralelas (por exemplo, uma versão LTS e uma estável) e [19] são monorepos com vários pacotes, a predecessora não é simplesmente a release publicada imediatamente antes: definimos como predecessora a maior versão menor ou igual à de R, com o mesmo prefixo de tag, entre as releases publicadas antes de R. A variante cronológica, mais literal, é mantida para comparação. A heurística inicial (v1) marca uma release como corretiva quando (i) a versão muda apenas no número de *patch* do Versionamento Semântico em relação à predecessora e (ii) pelo menos um commit entre as duas tem `fix`, `hotfix` ou `revert` como palavra inteira no título. Testamos [12] versões da heurística, combinando os dois pareamentos com seis critérios (Tabela [X]), e escolhemos a versão final pelo F1 contra a amostra-ouro (Seção [Validação manual]). A versão final, [nome], obteve precisão [P], recall [R] e F1 [F1].

*Tempo de recuperação (RQ 04).* As execuções de cada workflow são ordenadas cronologicamente. Um episódio de falha começa na primeira falha após um sucesso (`run_started_at`) e termina na próxima execução bem-sucedida do mesmo workflow (`updated_at`). O valor do repositório é a mediana, em horas, de todos os episódios encerrados de todos os seus workflows. Falhas que precedem o primeiro sucesso da janela não abrem episódio, porque o início real está fora da janela.

*Censura.* Episódios de falha sem sucesso até o fim da janela, e releases publicadas nos últimos 7 dias dela, não são descartados: são registrados como censurados e reportados [proporção mediana de episódios censurados por repositório: X%]. Descartá-los faria os repositórios parecerem mais rápidos para se recuperar e mais estáveis do que de fato são.

*Coleta.* A janela de workflow runs é consultada mês a mês. Como a API devolve no máximo 1.000 resultados por consulta filtrada, um mês que atinge esse teto é dividido ao meio (por dias e, dentro de um dia, por horário) até cada parte caber [N meses divididos; nenhum ficou no teto]. Todas as respostas da API são armazenadas em cache local, o que permite retomar a coleta após interrupções e reexecutar o pipeline sem novas chamadas.
